# CineFlow — Agent Entry Point

**If you are an AI coding agent working in this repository, read this file first, every session.**

This file is the router. It is deliberately short so it survives context pressure. It does not restate rules — it tells you which file owns each kind of truth, and what you are forbidden to do without approval.

---

## 1. What we are building

A **cinema box-office ticketing system**. A cashier at a counter selects a showtime, sees a live seat map, reserves seats, takes payment, issues a ticket. Two cashier terminals, one SQL Server Express instance, LAN only.

C# / .NET Framework 4.7.2 / WinForms / SQL Server Express. Three-tier: UI → BLL → DAL → stored procedures.

**Not** a website. **Not** a mobile app. **No** API tier. **No** real payment gateway. **No** real customer personal data. If a task seems to require any of those, stop and ask — it is out of scope by explicit decision, not by oversight.

## 2. Why we are building it this way

This is an academic capstone that has to be **defended orally**. Its thesis is a single claim:

> Two cashiers clicking the same seat at the same moment can never both succeed — and that is provable on demand, not merely asserted.

Every architectural decision serves that claim. Correctness under concurrency outranks feature count, UI polish, and delivery speed. A feature that cannot be demonstrated as correct is worth less than no feature.

Second, load-bearing fact: **this project is built with AI agents.** The documents in this repo exist because agent-authored code fails in a specific way — a mechanism that looks like a check but does not actually check. Three such defects were found in this spec before a line of it ran. The harness is calibrated against that failure mode, which includes yours.

## 3. Where truth lives — exactly one file per kind

| I need to know… | Read | Never infer it from |
|---|---|---|
| Table DDL, constraints, indexes, procedure signatures, error numbers, test specs | `DATA-CONTRACT.md` | existing code, your memory of it |
| Coding rules IS-01…IS-05, LO-01, PC-01, VG-01 | `IMPLEMENTATION-STANDARDS.md` | this file, chat history |
| What is already built and verified | `CURRENT_STATE.md` | the filesystem, your assumptions |
| Why a decision was made, and what was rejected | `DECISIONS.md` | first principles |
| Scope, delimitations, deployment topology | `Docs/WEEK0-DEFENSE-PACK.md` | — |

**Non-duplication rule.** Each fact lives in exactly one file. If you find the same rule stated in two places, that is a defect — report it, do not "helpfully" sync them. If you need a fact that lives in another file, link to it; do not copy it.

## 4. Before you start any task

Answer these six, in writing, before writing code. If you cannot answer one, stop and ask.

1. **What** am I building? (the concrete deliverable)
2. **Why** — which part of the thesis in §2 does it serve?
3. **What is already decided** that constrains it? (cite `DATA-CONTRACT.md` / `DECISIONS.md`)
4. **What must not change?** (see §5)
5. **What am I allowed to change** in this task? (files, explicitly)
6. **How will we verify it?** (which gate or test proves it)

If the task conflicts with anything in `DATA-CONTRACT.md` or `DECISIONS.md`, **name the conflict before implementing**. Do not resolve it yourself.

## 5. Change boundaries — frozen without explicit human approval

You may not modify these. Not to fix a build, not to make a test pass, not because a cleaner design exists.

| Frozen | Why |
|---|---|
| Anything in `Tests/` or `Deploy/` | These are the graders. Editing them destroys the only independent evidence. If a test is wrong, say so and stop. |
| Procedure parameter names, order, types, precision, defaults | Gate 2 enforces a per-parameter manifest. Signature changes silently break callers. |
| Any `CHECK` constraint, unique index, or primary key | These are the correctness guarantees, not obstacles to it. |
| `DATA-CONTRACT.md`, `IMPLEMENTATION-STANDARDS.md`, `DECISIONS.md` | Human-owned. Propose changes; do not make them. |
| `*.Designer.cs`, `*.resx` | Generated by the Visual Studio designer. Your edits get overwritten or corrupt the form. |
| `.csproj`, `.sln` | Human-owned. Non-SDK-style project files are easy to corrupt. Ask for a file to be included. |

**Three specific prohibitions**, because they are the ones agents actually violate:

- **Never** use dynamic SQL. Not `sp_executesql`, not `EXEC(@sql)`, not for optional filters. It silently breaks ownership chaining and the app login dies at runtime. Use the null-coalescing pattern in `IMPLEMENTATION-STANDARDS.md` IS-01.
- **Never** use `WITH NOCHECK`, `NOCHECK CONSTRAINT`, or drop a constraint to get past an error. If data violates a constraint, **the data is wrong**. Gate 2 fails on `is_not_trusted`.
- **Never** let a procedure return an empty result set on any path. Exactly one row, or `THROW`. An empty return means the cashier sees neither a ticket nor an error (PC-01).

## 6. Protecting completed work

A milestone marked **VERIFIED** in `CURRENT_STATE.md` is a stable foundation. Before changing anything inside one, answer:

1. What exists now?
2. Why does it exist? (`DECISIONS.md`)
3. What depends on it?
4. Does the request actually require changing it, or can it be additive?
5. Which test proves the current behavior?
6. What new test is needed?

Do not rewrite working code because you would have written it differently. Do not re-implement something already listed as done — **read `CURRENT_STATE.md` first, specifically to avoid repeating completed work.**

## 7. After every task — required report

No task is complete until you have produced all of this:

1. **Files written** — full paths, line counts. Name anything touched outside the allowed set.
2. **Raw tool output** — actual `sqlcmd` / build / test console text with error numbers and line numbers. Not a summary. Not "ran successfully." If you fixed and re-ran, show both runs.
3. **Raw `Deploy\verify.bat` output** — complete and unedited, including failing gates.
4. **Deviations from `DATA-CONTRACT.md`** — one row each: what the contract said, what you wrote, the engine error that forced it, and `SYNTAX-ONLY` or `SEMANTIC`. Write "None" if none. Do not omit small ones.
5. **Self-audit** — for each of IS-01…IS-05, LO-01, PC-01: compliant yes/no/N-A, plus the **file and line numbers that prove it**. Quote the lines. "I followed IS-01" is not evidence.
6. **Uncertainties** — what you guessed, what was ambiguous, what you expect to break later. If nothing, say so explicitly.
7. **`CURRENT_STATE.md` update** — propose the diff. Do not mark anything VERIFIED that a gate did not prove.

**A red gate reported honestly is worth more than a green one you engineered.** If you cannot make something pass, say so and show the failure. Never disable, comment out, or weaken a check to reach green. Never proceed to the next phase intending to come back.

## 8. Behaviors that will get your work reverted

- Redesigning something that already has a contract entry
- "Improving" scope without being asked
- Reporting green gates without pasting the console output
- Claiming compliance without line-number evidence
- Silently widening a column, renaming a constraint, or reordering a parameter
- Reintroducing an option listed as **rejected** in `DECISIONS.md`
- Editing a test so the implementation passes
- Continuing work from memory instead of re-reading `CURRENT_STATE.md` at session start

## 9. Session handoff — you are not the only agent on this project

This project is built across **many sessions, by different models and different agent tools.** A session may end abruptly when a context or token limit is reached. The next session may be a different model with **no memory of anything you did.**

Therefore:

**Your chat context is not project memory. This repository is.** Anything you learned, decided, discovered, or half-finished that exists only in your conversation is **lost** the moment the session ends. If it matters, it must be written to a file.

### At the start of every session

1. Read this file, then `CURRENT_STATE.md`.
2. Run `git log --oneline -10` and `git status` to see what actually happened last, rather than trusting any recollection.
3. Trust the files over your memory, always. If your memory says a milestone is done and `CURRENT_STATE.md` says WRITTEN, it is **WRITTEN**. Re-verify rather than assume.
4. If the repo state and the human's request disagree, say so before acting.

### At the end of every session, or when you are running low on context

Stop working and produce a **HANDOFF** block. Do not spend your last tokens on more code — an unrecorded half-finished change is worse than no change, because the next agent cannot see it.

```
HANDOFF
- Milestone:            (e.g. M1, in progress)
- Completed this session, with the gate output that proves it:
- Left incomplete, and exactly where it stops:
- Files modified:
- Gates last run, and their real results:
- Open questions for the human:
- The single next action the next agent should take:
```

The human pastes this to the next session. A `CURRENT_STATE.md` diff proposal is part of it, not a substitute for it.

### If you are mid-task and context is running out

Prefer **stopping at a clean boundary** — a file finished, a gate run — over pushing further. Never leave a migration partially applied to the database without saying so explicitly in the HANDOFF. The database is state that no file records; an unrecorded partial apply is the single worst thing you can leave behind.
